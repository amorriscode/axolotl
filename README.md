# Axolotl

Write [Anchor](https://www.anchor-lang.com/)-compatible Solana programs in a strict TypeScript subset.

The 2022 prototype parsed TypeScript with SWC and printed the AST. It never emitted a program. This tree replaces that compiler. You write instructions as exported functions, Axolotl lowers them to Anchor Rust, and the Agave toolchain produces the sBPF binary plus the Anchor IDL that existing clients already speak.

```ts
export function increment(
  counter: Account<Counter, { mut: true; hasOne: ["authority"] }>,
  authority: Signer,
): void {
  counter.count = counter.count + 1n;
}
```

## Why Anchor Rust, not a custom sBPF backend

sBPF v3, the syscall surface, and the program loader move with Agave. A hand-written backend would have to track all of that, and it still would not emit an Anchor IDL. Generating Anchor Rust keeps the output auditable, lets `anchor build` own binary correctness, and produces discriminators that match `sha256("global:instruction")[..8]`. The compiler itself is TypeScript, using the TypeScript compiler API, so the CLI and the browser playground run the same code.

Pinned today: Anchor **1.2.2**, Agave **4.1.2** (platform-tools v1.57, sBPF v3). See [toolchain.json](toolchain.json).

## Language

Programs are a documented subset: exported functions, account constraints in type arguments, integers, `Pubkey`, `bytes32`, `if`, one loop form, `require`, `emit`, `log`, system transfers, SPL `transferChecked`, and CPI. The rules, including what is rejected, are in [docs/language.md](docs/language.md).

`camelCase` names become `snake_case` in Rust and in the IDL, matching Anchor. Integer math is checked and fails with `ArithmeticOverflow` instead of wrapping.

## CLI

```sh
npm install
npm run build -w @axolotl-sol/cli   # optional; node runs the TypeScript directly
export PATH="$HOME/.local/share/solana/install/active_release/bin:$HOME/.local/bin:$PATH"

axolotl init my_program
cd my_program
axolotl build          # TypeScript -> Anchor Rust -> target/deploy/my_program.so
axolotl test           # build, then tests/*.test.ts on LiteSVM
axolotl deploy --cluster localhost
axolotl compile src/my_program.ts
```

`axolotl build` needs the Anchor CLI and Agave (`solana` / `cargo-build-sbf`). `axolotl compile` and the playground do not. Install them with:

```sh
sh -c "$(curl -sSfL https://release.anza.xyz/v4.1.2/install)"
curl -sSfL -o "$HOME/.local/bin/anchor" \
  https://github.com/otter-sec/anchor/releases/download/v1.2.2/anchor-1.2.2-x86_64-unknown-linux-gnu
chmod +x "$HOME/.local/bin/anchor"
```

Host `rustc` must be new enough for Anchor proc macros (1.89 or later; 1.99 is what this repo was built with). The sBPF crate itself is compiled by platform-tools, not the host compiler.

When `anchor build` fails, Axolotl rewrites `lib.rs` line numbers through `target/axolotl/sourcemap.json` so the message names the TypeScript line.

## Conformance

[CONFORMANCE.md](CONFORMANCE.md) is generated by `npm run conformance`. The current scoreboard is **20 / 32 (62.5%)**: every implemented feature passes on LiteSVM 1.6.1, and the remaining rows are unsupported on purpose (zero-copy, Token-2022 extensions, remaining accounts, direct sBPF, and the rest listed in that file).

The IDL check compares Axolotl's discriminators, event discriminators, and error codes with the JSON from `anchor build`.

## Staying current

[`.github/workflows/ci.yml`](.github/workflows/ci.yml) runs on every pull request: compiler tests, a full program build, the conformance suite, and the site build.

[`.github/workflows/toolchain-update.yml`](.github/workflows/toolchain-update.yml) runs every Monday. It reads the stable Anchor crate, the latest stable Agave release, and the npm `latest` tags for `@solana/kit`, `@solana/web3.js`, `@anchor-lang/core`, `@coral-xyz/anchor`, `litesvm`, and `typescript`. If any of those moved, it updates `toolchain.json`, the CLI defaults, example `axolotl.toml` files, and the testing package, rebuilds the programs, reruns conformance, and opens a pull request with the bump and the scoreboard.

No repository secret is required. The workflow uses the default `GITHUB_TOKEN`. A pull request opened that way does not start other GitHub Actions workflows, so the update job itself is the test run. If you want that pull request to trigger CI as well, store a fine-scoped PAT as `AXOLOTL_UPDATE_TOKEN` and point the workflow's `token` input at it.

`@coral-xyz/anchor` is pinned but stale at 0.32.1. The maintained JavaScript client is `@anchor-lang/core`, which tracks Anchor 1.2.2. Axolotl encodes instructions itself and does not depend on either client at runtime.

## Site

[site/](site/) is a static learning site: accounts, programs, PDAs, CPI, tokens, the compiler pipeline, an in-browser playground, and the live scoreboard.

```sh
npm run site:build
npx vite preview --host 127.0.0.1 --port 4173 --outDir dist
# from site/, or: npm run preview -w site
```

[`.github/workflows/pages.yml`](.github/workflows/pages.yml) deploys `site/dist` to GitHub Pages for this repository (`https://amorriscode.github.io/axolotl/`). Pages has to be enabled in the repository settings (Settings → Pages → GitHub Actions) before the first deploy succeeds. The workflow needs no extra secrets.

## Layout

```
packages/core       types and compiler intrinsics
packages/compiler   TypeScript subset -> Rust, IDL, client module
packages/cli        axolotl init | build | test | deploy | compile
packages/client     Borsh encode/decode for the generated IDL
packages/testing    LiteSVM helpers
examples/           counter, token vault, PDA profile, CPI
conformance/        feature program and scoreboard inputs
site/               learning site
```

`axolotl build` also writes `target/client.ts`, a small module that encodes instructions through `@axolotl-sol/client`.
